## 1. 这个版本是什么

微信桌面版 4.x（WCDB / SQLCipher 4）本地数据库的**离线**解密与聊天记录提取工具，Node.js 跨平台实现（Windows / macOS）。

核心能力：

| 能力 | 说明 |
|------|------|
| 统一密钥模型 | passphrase（32 字节）→ 每库独立 `enc_key = PBKDF2-HMAC-SHA512(passphrase, 该库首页 salt, 256000, 32)` |
| 纯 JS 解密后端 | SQLCipher 4 页面格式逐页 HMAC 校验 + AES-256-CBC 解密，**无需原生编译**，Win/Mac 行为一致（实测约 150 MB/s） |
| 四种取密钥通道 | `--key` 手动 / `--dump` 内存 dump / `--allow-memory-scan` Windows 实时扫描 / `--mac-frida` macOS 启动拦截 |
| 消息提取 | zstd 解压、`local_type` 低 32 位、跨版本列名兼容、`wxid_xxx:\n` 前缀反推发送者与「本人」判定 |
| 报告 | 自包含单文件，全字段转义；**html / md / json 多格式**，`-f, --format` 可一次产出多种，`--template <file.js>` 支持自定义模板 |
| 一键流水线 | `pipeline`：取密钥 → 解密 → 提取 → 报告 |
| Agent 技能 | 根目录 `SKILL.md` 遵循 Agent Skills 标准，可从 GitHub 安装 |

**适用边界**：仅读取你自己设备上的数据；不支持媒体 `.dat` 原文件；仅微信桌面版 4.x。

## 3. 安装与升级

```bash
git clone <本仓库地址>
cd wechat-wcdb-node
npm install            # @foxglove/wasm-zstd / better-sqlite3 / commander / koffi
npm test               # 期望：41 通过 / 0 失败

```

- 解密走纯 JS 后端，**不需要**编译任何原生模块。
- （可选）`npm install sqlcipher` —— 仅当纯 JS 后端在个别微信版本异常时作为回退；该包依赖 GitHub SSH 源，部分环境会拉取失败。

从 0.1.0 升级：命令与产物兼容，无破坏性变更，`git pull` + `npm install` 即可；两点新增可见行为 —— 报告默认仍输出 html，但可用 `-f html,md,json` 一次产出多格式（同基准路径、扩展名按格式改写）；`npm test` 断言数由 17 增至 **41**。

## 4. 快速上手

```bash
# 已知 passphrase（推荐路径）
node bin/wcdb.js decrypt --dir <db_storage 目录> --key <passphrase_hex> --out plain/
node bin/wcdb.js extract --db plain/message_0.plain.db --username wxid_目标 --self-wxid wxid_本人 --out messages.json
node bin/wcdb.js report --in messages.json --out report.html

# 一键（取密钥 → 解密 → 提取 → 报告）
node bin/wcdb.js pipeline --username wxid_目标 --self-wxid wxid_本人 --key <passphrase_hex>
node bin/wcdb.js pipeline --username wxid_目标 --dump wcdb_blob.bin
sudo node bin/wcdb.js pipeline --username wxid_目标 --mac-frida
```

数据目录不传 `--dir` 时按平台自动定位（Windows 读 xwechat `config/*.ini`；macOS 通配沙盒目录，缺「完全磁盘访问权限」会给出明确提示）。

## 6. 已知问题与本版本缓解措施

下列问题的完整定位与修复方案见 [../code-review.md](../code-review.md) / [../code-review-fix-plan.md](../code-review-fix-plan.md)。将在后续版本（建议 1.0.1 / 1.1.0）修复。

### 0. macOS `--mac-frida` 首跑必然失败（前置条件缺失，非 bug）

真实报错（attach 阶段，早于挂 PBKDF2 hook）：

```
等待微信进程出现（请在 90 秒内从 ~/Applications/WeChat.app 启动微信）...
错误：Unable to access process with pid 1170 from the current user account
```

本机只读诊断结论：

| 检查 | 结果 |
|------|------|
| `~/Applications/WeChat.app` | **不存在** —— 重签名这一步从未做，而 frida 方案依赖它 |
| `/Applications/WeChat.app` 授权 | 有 `app-sandbox` / `application-identifier` / `team-identifier` / `allow-jit`，**无 `com.apple.security.get-task-allow`** |
| 签名 flags | `0x10000(runtime)` → hardened runtime |
| `csrutil status` | **enabled** |
| 运行身份 | 非 root |

SIP 开启 + 目标无 `get-task-allow` 时，`task_for_pid` 一定被拒；**加 `sudo` 也解不开**，必须先重签名。恢复步骤（需你本人操作，触碰系统安全边界）：

```bash
npm install frida                                  # 主仓库 node_modules 里没有它
cp -R /Applications/WeChat.app ~/Applications/
codesign -d --entitlements :- /Applications/WeChat.app > ~/wx_ent_orig.plist
# 编辑 ~/wx_ent_orig.plist → 存为 ~/wx_ent.plist：
#   新增 com.apple.security.get-task-allow = true
#   删除 com.apple.application-identifier 与 com.apple.developer.team-identifier
#   务必保留 com.apple.security.app-sandbox（删掉会让微信切到另一数据目录，读不到已有记录）
codesign --force --deep --sign - --entitlements ~/wx_ent.plist ~/Applications/WeChat.app
```

然后**完全退出原版微信**（否则命中的仍是不可调试的进程），再：

```bash
sudo node bin/wcdb.js key --mac-frida -o keys.json
# 立刻从 ~/Applications/WeChat.app 启动微信（rounds=256000、passwordLen=32 的那次 PBKDF2 只在启动瞬间发生）
```

不想动签名的替代方案是关闭 SIP，属降级整机安全，**不推荐**；更省事的是已有 passphrase 时直接用 `--key`。

本版本同时修掉了这条路径上的两个代码缺陷（改动在工作区，尚未提交）：attach 失败现在会输出上面这套「是否 root / SIP / 有无 get-task-allow / 命中的是不是未重签名副本」的可操作诊断，而不是一句 frida 原生英文错误；微信进程匹配改为按主二进制完整路径精确匹配（原先 `pgrep -f` 的特征串在本机会命中 10 个微信相关进程，包括 `WeChatAppEx`、`WeChatHelper`、`crashpad_handler`，取到 Helper 就会表现为「抓取超时」这种更难排查的失败）。

### C-1 内存 dump / 扫描取密钥在本版本实际不可用

候选生成对每个字节偏移无条件跑 4 次 PBKDF2。实测单偏移 81.75 ms：

| dump 大小 | 预计耗时 |
|-----------|----------|
| 1 KB | ≈ 84 s |
| 4 KB | ≈ 5.6 min |
| 64 KB | ≈ 87 min |
| 1 MB | ≈ 24 h |

**缓解**：本版本请优先使用 `--key <passphrase_hex>`（跳过候选生成，代价仅每库一次 KDF + 首页校验）。Windows 若只能走 dump，请把 dump 严格限定在 `Config.Cipher` 附近的小块，不要导出整个内存区域；`--allow-memory-scan` 会扫描最大 64 MB 的整块区域，请勿在本版本用于真实规模。

### C-2 / M-5 密钥文件权限与 stdout 泄露

passphrase 默认写入 `os.tmpdir()/wxdb/passphrase.hex`（0644），`keys.json` 同为 0644，且 `key` 命令会把首个候选密钥原文打印到 stdout。

暴露范围随调用方式而变（实测 + 代码事实）：

- 普通终端：`os.tmpdir()` 是**私有 per-user 目录**（`$TMPDIR`，如 `/var/folders/…/T/`），他人一般读不到，风险主要是 0644 + 路径可预测。
- **文档主推的 `sudo node bin/wcdb.js key --mac-frida`**：sudo 默认会重置 `TMPDIR`，`os.tmpdir()` 回落到 `/tmp`，即 `README.md:108` 自述的 `/tmp/wxdb/passphrase.hex` —— 世界可读写目录下新建 0755 目录 + 0644 文件，**同机任意本地用户可读**。（此分支未实测，需 sudo 密码。）
- `keys.json` 写在当前工作目录，与是否 sudo 无关。

**缓解**：

```bash
umask 077                                   # 让新建文件/目录默认不可被他人读
node bin/wcdb.js key --dump blob.bin -o ~/.wcdb-local/keys.json
chmod 600 ~/.wcdb-local/keys.json           # 已存在的文件补一次收紧
# 用 -o 指向自己的私有目录；绝不要放进云同步/共享目录（iCloud、Dropbox、仓库工作区）
# sudo 抓取后立刻清理共享临时目录里的副本（路径以实际输出提示为准）
rm -f /tmp/wxdb/passphrase.hex "$TMPDIR/wxdb/passphrase.hex" 2>/dev/null
# 不要把 key 命令的 stdout 记入日志/录屏；改用文件消费密钥
```

### C-3 `decrypt` 子命令错误提示与退出码失效

`decrypt` 未 `await` 内部异步任务：失败时输出裸栈而非「错误：…」提示，且命令返回可能早于明文写完。

**缓解**：优先用 `pipeline`（该路径已正确 `await`）；若必须分步，执行 `decrypt` 后**显式核对产物**再进入 `extract`：

```bash
node bin/wcdb.js decrypt --dir <db_storage> --key <hex> --out plain/
ls -la plain/          # 确认 *.plain.db 存在且大小与源库相当，非 0 字节残留
```

### M-1 大库解密内存

整库读入 + 同尺寸输出缓冲，峰值约 2–3× 文件大小。

**缓解**：对 500 MB 以上的 `message_*.db`，先用 Node 的大堆运行：`node --max-old-space-size=8192 bin/wcdb.js decrypt ...`，并确保机器有该量级空闲内存（Buffer 在堆外，`--max-old-space-size` 只兜住 JS 堆，实际仍受物理内存约束）。

### M-2 / M-3 / M-4 / M-6

- `--out` 路径避免含单引号 `'` 的目录名（M-2）。
- 未安装 sqlcipher 时，若解密失败报「缺少 sqlcipher 原生模块」，真实原因很可能只是 passphrase 不对 —— 先回到 `--key` 核对密钥（M-3）。
- 大会话表提取偏慢/内存偏高，因同表被扫描解压两次；必要时按库分批提取（M-4）。
- macOS frida 抓取成功后进程可能仍存活至 90 秒定时器到期，可安全 `Ctrl-C`（passphrase 已落盘）（M-6）。
